# CoreFit performance: BEFORE report (2026-11-15)

Status: **tooling and static audit done; production read APIs measured (section 2).** The cloud sandbox
cannot reach `api.vinven.net`, a phone, the Supabase dashboards or Cloudflare analytics, so measurements come from
Venkat's side. The per-API table in section 1 still shows "_pending_" for calls that are not run on production
(writes, edge functions, admin); read the timings of the measured calls in section 2.

Code state: `develop` at 9732674 (app 1.2.3). Raw data: `docs/perf/raw/`.

## 1. Inventory (done, offline)

`node scripts/perf/inventory.mjs` found 206 call sites, **139 distinct APIs** in `src/` and `web/src/`:
107 `.rpc()` sites (96 distinct RPCs, about 31 read-only and 65 that write), 56 table reads,
35 table writes and 9 edge-function invokes (11 functions exist; `join`, `send-push` and
`razorpay-webhook` are called by others, not the app). 24 call sites have no hook (called from
screens, stores or edge code). Realtime: **none** (no `channel()` or realtime use in the app).

pg_cron (all in migrations): `corefit-reminders` 5 min, `corefit-enquiry-reminders` 5 min,
`corefit-auto-check-out` 10 min, `corefit-birthdays` hourly :05, `corefit-nudges` hourly :15,
`corefit-purge-logs` daily. About 36 triggers; the write-heavy ones are the `notifications`
statement trigger (pg_net to `send-push`), `attendance_worked_minutes`, `memberships_number_receipt`
and the `require_paid_branch` guards.

Full table (type, R/W, api function, hooks, screens): `docs/perf/raw/inventory-2026-11-15.json`, and the
per-API table below. "When" per call is in the JSON's hook; roughly: app start = profile,
`contact_details`, `is_platform_admin`, `my_gym_invites`, `branch_access`, notifications; screen open =
everything else; focus = any query older than the 30 s default staleTime refetches when the app
returns to the foreground; user action = every write.

## 1b. Measured on production (2026-11-15, daytime run)

Run from Venkat's Mac through `api.vinven.net` with the anon key and the four "CoreFit Perf Test" logins
(owner, supervisor, trainer, member). Read-only, one request at a time, 250 ms gap, 2 warm-ups + 20 runs per call,
started 03:59 UTC (9:29 IST) with `--allow-peak`, so this is a **daytime** run: the AFTER run must also be run in the daytime.
Zero errors; every call returned 200. Data: one gym, 304 people, ~11.4k attendance rows (a small gym). Raw: `docs/perf/raw/bench-production-2026-11-15.json`.
Cells are **p50 / p95 in ms**; size is the largest across roles. Admin and write APIs are not run on production (develop only).

**What the numbers say**

- **The floor is about 180-200 ms** (p50 of `is_platform_admin`, `enquiries`, `trainer_busy_slots`, which do almost no work). That is
  the round trip from this Mac through Cloudflare to Supabase. Almost every call is within 20-70 ms of it, so on this small data set
  the database itself is fast and **time is dominated by the number of round trips**, not by query cost.
- Home screens mount 11-13 queries: at about 200 ms each that is 2-2.5 s of waiting if they run one after another, and each one adds
  radio time on a phone. Merging requests and not refetching unchanged data (fix plan #5 and #2) is the biggest lever.
- **Heaviest calls (p50):** `export_attendance` 686 ms (1,000 rows, 143 KB), the exercise library 627 ms for the owner's first
  call (48 KB, 103 rows; 194-253 ms for the others, so the first call is partly cold), `gym_attendance` 322 ms (78 KB),
  `member_trainers` 302-321 ms (41 KB), `export_memberships` 293 ms, `member_insights` 283 ms, `gym_people` 224-281 ms (136 KB for 304 rows).
- **Payload, not time, is the cost on 4G:** `gym_people` 136 KB, `export_attendance` 143 KB, `gym_attendance` 78 KB,
  `member_insights` 58 KB, `attendance_report` 52 KB, exercises 48 KB (fetched by every role), `member_trainers` 41 KB.
  A trainer's notifications inbox is 30 KB (100 rows).
- **Spikes (p95/max) look like network jitter**, not queries: `membership_plans` max 4.7 s with p50 272 ms, `work_permissions`
  max 3.7 s, `saved_offers` max 2.6 s, all tiny tables. They are single outliers; p95 stays under 2 s everywhere (limit was 5 s).
  Worth repeating the run once at another hour before drawing conclusions about them.
- Per-role sums of p50 (one pass of every call in the list, not what a screen does): owner 10420 ms (43 calls, 735.3 KB),
  supervisor 6273 ms (30 calls, 358.1 KB), trainer 4065 ms (20 calls, 120.8 KB),
  member 4326 ms (21 calls, 49.7 KB).
- Not measured yet: how this grows with a bigger gym (RLS and FK-index work shows up there, not at 304 people), phone cold start,
  per-screen time, edge functions and writes (develop only), web dashboard load, Cloudflare analytics.

## 4. Database (migrations plus the Supabase advisor, production, 2026-11-15)

- **42 RLS policies** call `auth.uid()` per row instead of `(select auth.uid())` (advisor `auth_rls_initplan`, listed
  in the DB Stats CSV). An earlier draft said 314; that counted every use in RPC bodies too, which are not affected.
  The policies also call stable security-definer helpers (`has_gym_role`, `is_coach`, ...) directly.
- **51 foreign keys have no covering index** (advisor `unindexed_foreign_keys`). 3 unused indexes: leave them, traffic is low.
- **192 `multiple_permissive_policies` warnings**: several SELECT policies on the same table are OR-ed on every query.
  Merging them is the riskiest change (it can alter who sees what), so it goes last and only with the `supabase/tests/` checks.
- Unpaginated reads: `gym_people`, `member_insights`, `export_*`, `trainer_hours_month`, `trainer_requests`,
  `member_trainers`, `trainer_profiles`, `exercises` (library), `bookings`. Capped: enquiries 1000,
  workout logs 100, measurements 366, notifications.
- Still missing: `db-stats.sql` queries 1-4 (top statements by total and mean time, cache hit ratio, table sizes). They show real
  slow queries and need to be run on production and sent as CSV.
